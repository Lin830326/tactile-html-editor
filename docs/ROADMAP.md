# Roadmap

This document records the direction that has been decided and the order of the work. Read it before each new session starts.

Last updated: 2026-11-11.

## Goal

People in companies dare to use the HTML reports and slides that AI produces, and can change them.

There are 2 problems now:

1. It cannot be changed. The person who receives HTML from an AI agent cannot change it, and can only go back to Claude Code or Cursor to have it made again.
2. It cannot be trusted. A number in a report may be an AI hallucination, and the reader cannot know where the number comes from.

There are 2 matching solutions:

1. The editor: edit HTML the way Acrobat edits PDF. Change it by hand, export it, pack it.
2. Provenance and reconciliation: every number can be clicked back to its source. The program computes the rules again; the AI does not vouch for them.

## Audience

- A: people who produce HTML with AI agents such as Claude Code and Cursor. A is the channel that spreads the product.
- B: the company users who receive this HTML. B does not write code, and the value of the product is with B.

## What has been decided

| Item | Decision |
|---|---|
| License | MIT |
| When to go public | Only after all the ideas are finished. Until then the repo stays private |
| How to go public | Create 1 new public repo with only 1 clean commit, authored with GitHub's anonymous email address. The old repo stays private |
| Online version | Not on a domain that is shared with other web pages |
| Editing PDF files directly | Not done. Only PDF export |
| Packages | 2 packages: the editor (a single offline file) and the ingest side (needs Node) |
| Library that reads Excel | SheetJS 0.20.3, with the package file in `ingest/vendor/`. Reason: 0.18.5 on npm has 2 known vulnerabilities that are not fixed |
| Verification | Done by the program. The AI must not vouch for correctness |
| Precision of provenance | A cell or a page number, for example `2026Q3.xlsx › Income › D14` |
| Citing numbers | In the first version, the AI can cite a number only by ID, and must not write numbers itself. The program fills in the actual value |
| Intermediate format | 2 layers. The structure layer is JSON, for programs: values, addresses, formulas. The reading layer is MD, for the AI, and every value carries an ID |
| YAML | Only for files that people read, change and sign off: the reconciliation rules and the report settings |
| Charts | Output is inline SVG, with no JS chart library. The program computes the coordinates from the data; the AI chooses only the type and the style |

## Order of the work

### Stage 1: B can use it (the editor)

1. The free-move switch and hints. Done: "Reorder" and "Free move" in the toolbar; dragging with `Alt` uses the other mode.
2. Export PDF and PNG. Done, in the export menu. "Export PDF…" opens the print dialog of the browser, with one page per slide for slides. "Export PNG picture" outputs the whole page, at the current device width. The Artifact version has PNG only.
3. Pack pictures and CSS with relative paths into a single file. Done: the hint after opening, and "Embed pictures and styles in the document…" in the export menu. The user chooses a folder, or drags a folder in. The editor embeds pictures, style sheets and fonts in the document, as 1 undo step. External scripts, audio and video files and embedded pages are not embedded; `http(s)` resources are not downloaded.

Items 2 and 3 each use 1 new session, one after the other. They must not be done in parallel, because every feature must rebuild `dist/`, and parallel work would conflict.

### Stage 2: people can trust it (provenance, smallest scope)

4. Write the specification of the structure layer JSON and the provenance attributes. The draft is done: `docs/spec/provenance.md`. In its section 11, 2 things wait for the owner to decide; they can be decided during implementation.
5. Make the ingest side a skill that supports Excel only. Reason: cell addresses are exact, with no ingest error. The `ingest` command is done, in the `ingest/` folder: it reads `.xlsx` and writes `facts.json` and `facts.md`. The `fill` command is also done: it fills in the numbers and embeds the provenance block. The `verify` command is done: it checks the report at 3 levels and writes which level it reached. The instruction file for AI agents is done: `ingest/SKILL.md`. Not done yet: one full run of the flow by a real AI agent that follows the instruction file.
6. Reconciliation rules in YAML, with only 2 types: a total (`sum`) and 2 cells that are equal (`equal`). "The report number equals the source value" is a fixed check and is not written in the rules file. Done: `fill --rules` reads the rules file, computes the results, and writes the rules into the provenance block. The examples are in `ingest/examples/`.
7. 2 features in the editor: click a number to show its source; a panel lists the rules that pass and fail. Done: `src/js/provenance.js`. A click on a number shows the source value, the row heading and column heading, the cell position and the formula. The "Sources" tab on the right lists the rule results and the status of each number. When a number is changed by hand, the editor marks it "Changed by hand" in the same undo step. Not done yet: Level 2 verification (comparing the SHA-256 of the source file), and a button that marks a number as "needs no source".
8. Chart generator: bar, line and pie, with SVG output. Done: `ingest/src/chart.mjs`. The draft has a `data-chart` element, `fill` computes the coordinates and draws the chart, and `verify` draws it again and compares. The editor checks the numbers on a chart, and a click on a shape shows the source. Not done yet: stacked charts; colors for dark backgrounds; drawing charts again in the editor.

The user may change a number that has provenance by hand in the editor. In that case the editor must mark it "Changed by hand", and must not keep the original provenance mark.

### Stage 3: expand

9. Add PDF and docx input. Both are done. docx: `ingest/src/docx.mjs` and `ingest/src/number.mjs`, with no new dependency. Tables are `t1`, `t2`…, paragraphs outside the tables are `body`, and a number in a paragraph has its own address. Word stores text only, so numeric values are parsed from the text by fixed rules; `facts.md`, `verify`, the MCP server and the editor all write this sentence. The specification is in section 3.3. PDF: `ingest/src/pdf.mjs`, with `pdfjs-dist` 6.5.438 (the owner chose it on 2026-11-12; 5.6.83–6.2.107 have 1 high-severity known vulnerability, GHSA-hq66-cqwq-w95j, and must not be used). The ingest side therefore needs Node 22.13 or later. An address is `p<page>/<column><line>`: the line is the number of the text line on the page, and the column is the position of the piece of text in that line; numbers inside text are in `p<page>n`. A PDF does not store tables, and the program works out the lines and columns from the coordinates. So a table row that has an empty cell moves to the left. All 4 places write this sentence. The specification is in section 3.4. Not done yet: tests with real financial report PDFs, aligning columns by x coordinate, text recognition for scanned files.
10. Add an MCP interface, so that the AI queries a file as needed. When a file exceeds the context size of the AI, the whole content does not have to be loaded at once. Done: `tactile-ingest mcp --facts <facts.json>`, in `ingest/src/mcp.mjs` and `ingest/src/query.mjs`. It talks over stdio and has 5 read-only tools: `list_sources`, `read_range`, `search_facts`, `get_facts`, `trace_formula`. No new dependency. It was tested with a client of the official MCP SDK 1.32.2. Not done yet: a real AI agent writing 1 full report through the tools; tools for `fill` and `verify`; HTTP transport.
11. Slide page management, compressing embedded pictures, and export after clean-up. Done: `src/js/pages.js` and `src/js/tidy.js`. The "Pages" tab on the left lists the slides, and can add, copy, delete and reorder them. "Compress embedded pictures…" in the export menu encodes data URL pictures again, as 1 undo step. "Clean up and export…" in the export menu downloads 1 copy. 4 kinds of content can be removed: comments, marks of the author and of the tool that produced the file, scripts, provenance data. Not done yet: slide thumbnails (now only the page number, the background color and the title are shown); selecting several slides at once; compressing CSS background pictures; removing CSS rules that are not used.

23. Floating island. Done (2026-11-14); the templates were finished on 2026-11-16 and share the same file as item 22. 1 group of pill buttons fixed to a corner of the window; the implementation is in `src/js/island.js` (`HE.island`), and the specification is in "Floating island (HE.island)" of `CONTRACT.md`.

## Known limits

- Tests cannot drag on the canvas with Playwright's `page.mouse`. Reason: while the mouse moves with a button held down, Playwright runs a script in every frame; the sandbox of the edit frame does not allow scripts, so that move does not return. `tests/move-mode.spec.js` sends mouse events inside the page instead, and new gesture tests can do the same.
- CI tests Chromium only. The whole suite of 157 tests was also run with Playwright's Firefox and WebKit (2026-11-18): 150 pass in Firefox and 150 pass in WebKit. Real Safari has not been tested.
- The 2 rendering differences in Firefox are explained (2026-11-19), and both come from the test environment: the display scaling of this computer is 120%, and Playwright's Firefox renders at 1.2 times but reports a ratio of 1. For a 696×646 frame, the inner viewport is 695.83×645.83px; a 4px border is drawn as 3px or 4px (`docs/drafts/ff-dpr.cjs`; a minimal page that has nothing to do with the editor behaves the same). The PNG height in `export.spec.js`: the `scrollHeight` of the canvas is 1583, the page is really 1584px high, and the picture is right; the test now uses the height of the root element and passes. `screenshot-check.spec.js`: the frame position that Playwright reports is 263.99997, 47.999996, the screenshot is off by 1px, and the test rounds the coordinates (`en-pitch` 8.1% → 1.2%); border rounding makes the boxes of `en-conference` 1–2px shorter, a difference of 6.4%, and the test still fails; the tolerance was not widened. Firefox has 7 failures left: 5 need features that only Chromium has, 1 needs scroll-linked animation, and 1 is the border rounding above. No test was run on a computer with 100% display scaling.
- The canvas in WebKit (Safari) uses a "guard frame" (2026-11-18, `GUARD_SANDBOX` in `canvas.js`). Cause: in a sandboxed frame without `allow-scripts`, WebKit runs no event listener at all, not even one that the outer page attached. Approach: when `deafFrames()` detects such a browser, the edit frame uses `allow-same-origin allow-scripts`, and the 1st element of the head is a CSP (`script-src 'none'; frame-src 'none'; object-src 'none'`); right after the frame loads, `sandbox` is changed back to `allow-same-origin`, so a page that the frame navigates to by itself cannot run scripts; the copy on the canvas drops the `http-equiv` of a refresh `<meta>` (the model and the exported file keep it). `tests/guard-frame.spec.js` makes Chromium take this path too, so CI can test it. Limits: nested pages do not load while editing; the content of `<noscript>` is not shown; the print frame (`copyFrame` in `fileio.js`, `hear: true`) uses the same approach. WebKit still has 6 failing tests: 5 need features that only Chromium has, and 1 expects a nested page to load. 3 rendering differences were explained and fixed. (1) The `.slide` of the slide templates used `aspect-ratio: 16 / 9` with `overflow: clip`; WebKit does not let such a box grow with its content, and at phone width up to 448px of content was cut off. It was changed to `min-height: 56.25cqw`, and the heights at the 3 widths are the same in WebKit and Chromium. (2) `vw` and media queries count the page scrollbar in the width, but `render()` in `snap.js` used the width without the scrollbar as the width of the `<svg>`, so text sized with `vw` was about 1.5% smaller in the captured picture. The `<svg>` now has the same width as the window (`innerWidth`). Every browser whose scrollbar takes width is affected; real Chrome on Windows has not been tested. (3) `screenshot-check.spec.js` used to scale the frame screenshot, with its scrollbar, to the width of the captured picture and then compare; it now captures the page area only. The PNG that was 20px short is explained and fixed: WebKit draws the frame's own scrollbar with the `::-webkit-scrollbar` rules of the parent page that match the `<iframe>`, so the 10px rule in `base.css` made the scrollbar of every frame take 10px, and the `NO_PAGE_SCROLLBARS` inside the frame could not remove it. The copy used for export was 10px narrower; the phone and tablet canvases were 10px narrower too (a 390px phone page had only 380px). The fix is in the parent page: `.fio-copy-frame::-webkit-scrollbar` in `fileio.css` and the non-desktop `.cv-frame::-webkit-scrollbar` in `canvas.css` are both `display: none`.
- The Firefox and WebKit failures that were not explained before are now explained (2026-11-18). 2 product problems, fixed: in Firefox, when `decode()` finishes the element has not yet taken the size of the new file, `sameLayout()` in `tidy.js` measured the old size, and the layout changed after compression (it now waits for the `load` event); WebKit does not hear the `afterprint` of the print frame (it now uses the guard frame). 3 test problems, changed: Firefox and WebKit refuse port 9 (59321 is used now); the mouse wheel of Playwright's Firefox scrolls only 563px at a time (`scrollTo` is used now); with scripts off, `toHaveJSProperty` cannot read the property in Firefox (`evaluate` is used now). 2 limits of the test tools: Playwright's Firefox crashes on a click after 16 MB of text is filled in (a blank page crashes too; Firefox now uses 12 MB), and Playwright's WebKit takes 25 seconds to fill in 16 MB (the time limit was widened); when the document is handed to the editor directly, both handle 16 MB in under 2 seconds. Firefox then had 8 failures left: 5 need features that only Chromium has, 1 needs scroll-linked animation, and 2 were rendering differences (explained on 2026-11-19, see the item above). The formerly unstable `key-storage.spec.js:146` is explained: a closed tab leaves an "in use" marker (`tactile:open:<id>`), and a new tab can see the autosave record, but `heldElsewhere()` treats it as belonging to another tab and holds it for 3 minutes. In Playwright's Firefox with 8 workers running at once, the write in `pagehide` that clears the marker did not arrive after the tab was closed (3 times in 40); `close({ runBeforeUnload: true })` is the same (3 times in 80). The test now sends `pagehide` before closing and confirms that the marker is cleared, and it passes 100 times out of 100. Whether real Firefox leaves the marker when a tab is closed has not been tested; if it does, the user must wait 3 minutes to see the previous document in a new tab.
- Of the 3 kinds of folder source of the embed feature, tests cannot control the folder picker of the system, and cannot simulate a real folder drop. Folder upload inside an Artifact has not been tested for real either.
